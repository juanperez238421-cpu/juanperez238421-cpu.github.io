PROYECTO CENTRAL · BLUE TEAM

Web Defense Lab — defender una aplicación bajo ataque controlado

El proyecto consiste en construir una aplicación web funcional, desplegarla dentro de un laboratorio aislado y someterla a tráfico hostil reproducible. El reto no es “hacer una demo de seguridad”: los estudiantes deben observar degradación real del servicio, diagnosticarla con evidencia y aplicar defensas hasta recuperar disponibilidad, estabilidad y trazabilidad.

El generador de tráfico hostil solo puede apuntar a servicios del laboratorio local/privado definidos por el docente. No se permiten dominios públicos, IP externas ni objetivos ajenos al entorno del curso.

1 · Web app Aplicación construida por el equipo: frontend + backend + datos de prueba.
2 · Reverse proxy Capa de entrada para límites, timeouts, headers y reglas defensivas.
3 · Telemetría Logs, métricas de latencia, tasa de errores, solicitudes por segundo y uso de recursos.
4 · Attack simulator Runner cerrado con escenarios predefinidos de carga hostil dentro de la red del laboratorio.
5 · Blue team Analiza, decide, endurece, prueba y documenta cada defensa.

Escenario A · HTTP flood controlado

El simulador incrementa progresivamente las solicitudes hacia una ruta costosa de la aplicación hasta producir saturación observable. Los estudiantes deben identificar el cuello de botella y defender el servicio.

Escenario B · abuso de autenticación

El laboratorio genera múltiples intentos inválidos contra cuentas ficticias. El objetivo es detectar patrones, reducir automatización abusiva y mantener el acceso legítimo disponible.

  • Rate limiting por identidad y origen.
  • Backoff temporal y bloqueo progresivo.
  • Logs diferenciados para éxito, fallo y bloqueo.
  • Mensajes de error que no revelen información sensible.

Escenario C · entradas hostiles

El runner envía datos inesperados, tamaños límite y formatos inválidos contra endpoints de prueba. La defensa debe demostrar validación estricta, manejo de errores y ausencia de caídas del proceso.

  • Allow-list de formatos y tamaños.
  • Validación server-side.
  • Timeouts y límites de payload.
  • Respuestas consistentes sin stack traces expuestos.

Defensas que deben justificar

  • Rate limiting y cuotas.
  • Timeouts, límites de conexión y tamaño de solicitud.
  • Caching cuando sea técnicamente válido.
  • Separación de responsabilidades entre proxy y aplicación.
  • Validación y control de errores.
  • Logs estructurados y señales de alerta.
  • Principio de menor privilegio para servicios y credenciales.

Prueba de defensa

Cada cambio debe compararse contra una línea base. Una defensa no se considera válida solo porque “parece funcionar”; debe mostrar evidencia antes/después.

  1. Ejecutar baseline sin ataque.
  2. Ejecutar escenario hostil controlado.
  3. Registrar degradación y causa probable.
  4. Aplicar una defensa concreta.
  5. Repetir exactamente el mismo escenario.
  6. Comparar métricas y explicar el efecto observado.

Arquitectura recomendada del laboratorio

El entorno debe ejecutarse en contenedores o máquinas locales del curso, con red interna y datos ficticios. El simulador de ataque no recibe una URL libre; el objetivo está fijado por configuración del docente.
