CLASS 4 · QA + LIVE DEFENSE

USB/offline QA + live project defense

The project is now treated as a product. The student runs a controlled failure matrix, fixes portability defects, documents the final architecture and performs a live defense from portable media or a clean folder.

THEORY 01

Testing is a claim-evidence pair

“It works” is not a test. A test defines initial conditions, an action, expected behavior and observed evidence.

Condition: network disconnected
Action: launch PORTABLE_BUILD
Expected: scene opens and all local effects work
Observed: PASS / FAIL + screenshot/log
THEORY 02

Fault injection

Good QA intentionally creates failures before the final presentation. Remove or rename a resource, corrupt config, move the folder and close the application repeatedly. The purpose is to expose assumptions while they can still be fixed.

THEORY 03

Live defense is reproducibility

The student should be able to change one documented parameter, relaunch and predict the visual result. That demonstrates ownership of architecture rather than memorization.

WORKSHOP

Final defense sequence

  1. Launch from clean/portable folder.
  2. Explain App → Scene → Effect → Config → Launcher.
  3. Show one effect class and its parameters.
  4. Change one visual parameter live.
  5. Relaunch and verify predicted behavior.
  6. Show QA matrix and one defect that was fixed.
