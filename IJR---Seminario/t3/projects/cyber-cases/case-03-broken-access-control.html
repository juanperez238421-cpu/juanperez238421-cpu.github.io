CASE 03 · BROKEN ACCESS CONTROL / IDOR

Autenticado no significa autorizado.

El endpoint identifica un usuario ficticio pero, en la versión inicial, no verifica que el registro solicitado le pertenezca. El estudiante debe demostrar el fallo y corregir autorización por objeto.

DevToolscurlRESTAuthorizationHTTP 403
Información sintética: los registros de Ana, Bruno y Camila existen únicamente dentro de este laboratorio.

1. Petición permitida

curl -i http://127.0.0.1:8080/api/records/1   -H "X-Lab-User: ana"

La respuesta representa a Ana consultando su propio registro.

2. Reproducción del fallo

curl -i http://127.0.0.1:8080/api/records/2   -H "X-Lab-User: ana"

En el baseline, Ana recibe el registro ficticio de Bruno. El cambio de 1 a 2 demuestra el fallo de autorización.

3. Repetir desde DevTools

  1. Abre DevTools → Network.
  2. Inspecciona la URL y headers.
  3. Usa “Copy as fetch” o “Copy as cURL” únicamente sobre localhost.
  4. Cambia solo el identificador del objeto.
  5. Documenta por qué autenticación y autorización son controles distintos.

4. Defensa requerida

En app/server.js, el endpoint debe verificar que found.owner === user. Si el registro existe pero no pertenece al usuario, responde con un resultado seguro y consistente; justifica si eliges 403 o 404.

Después agrega una prueba que garantice que Ana nunca obtiene un objeto de Bruno o Camila.

5. Verificación

# Debe seguir permitido
curl -i http://127.0.0.1:8080/api/records/1 -H "X-Lab-User: ana"

# Debe quedar denegado
curl -i http://127.0.0.1:8080/api/records/2 -H "X-Lab-User: ana"
