CASE 02 · AUTHENTICATION ABUSE

Credential Abuse: defender el login sin bloquear al usuario legítimo.

El laboratorio envía múltiples intentos inválidos reales contra cuentas ficticias. El objetivo es distinguir abuso automatizado, registrar evidencia y aplicar controles sin destruir la usabilidad.

TerminalHTTP 401Rate LimitBackoffLogsDevTools
Datos ficticios: este caso no usa credenciales reales ni servicios externos.

1. Confirmar comportamiento legítimo

curl -i -X POST http://127.0.0.1:8080/login   -H "Content-Type: application/json"   -d '{"username":"blue-team","password":"lab-only-password"}'

Registra el código HTTP y la respuesta. Este flujo legítimo debe seguir funcionando después del hardening.

2. Ejecutar abuso controlado

ATTACK_PROFILE=auth docker compose --profile attack run --rm attack > auth-before.json
docker compose logs --no-color web proxy > auth-before.log

Busca volumen de 401, frecuencia, repetición de identidades y origen del tráfico.

3. Inspección en navegador

  1. Abre DevTools → Network.
  2. Realiza un login válido y uno inválido.
  3. Compara request body, status y response headers.
  4. Verifica que el mensaje de error no revele si el usuario existe.
  5. Identifica qué señal podría utilizarse para limitar automatización.

4. Diseñar defensa

Implementa y justifica al menos dos controles: rate limiting, ventana temporal, backoff progresivo, bloqueo temporal, contador por identidad/origen ficticio, logs estructurados o alertas por umbral. No almacenes contraseñas en logs.

5. Validar

ATTACK_PROFILE=auth docker compose --profile attack run --rm attack > auth-after.json

Después repite el login legítimo. Una defensa que bloquea también el acceso válido no está terminada.

Pregunta de defensa oral

¿Qué diferencia existe entre limitar por IP, por identidad y por combinación de señales? ¿Qué falsos positivos puede producir cada estrategia?
