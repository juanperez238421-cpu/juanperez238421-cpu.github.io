CASE 04 · STORED HTML / XSS

Cuando los datos terminan convertidos en código.

El tablero local inserta comentarios directamente dentro del HTML. El estudiante debe inspeccionar el DOM, demostrar la inyección con un marcador inocuo y corregir la frontera entre datos y código.

HTMLDOMDevToolsOutput EncodingCSP
Payload de laboratorio: solo modifica un atributo del DOM local; no roba cookies, no exfiltra información y no debe reutilizarse fuera de este entorno.

1. Abrir tablero

http://127.0.0.1:8080/board

Abre DevTools → Elements y localiza .comment-text.

2. Demostración de inyección almacenada

Publica exactamente este marcador de laboratorio:

<img src=x onerror="document.body.dataset.labMarker='xss-triggered'">

Recarga. En DevTools → Elements, selecciona <body>. Si aparece data-lab-marker="xss-triggered", el navegador ejecutó contenido que debía tratarse como dato.

3. Inspección rigurosa

  1. Identifica dónde entra el comentario.
  2. Identifica dónde se almacena.
  3. Ubica dónde se concatena dentro del HTML.
  4. Explica por qué validar solo en el cliente no resuelve el problema.
  5. Distingue sanitización de output encoding.

4. Defensa

Corrige el renderizado para que el comentario se inserte como texto y no como markup. Después añade una Content Security Policy apropiada como defensa en profundidad. La solución principal sigue siendo separar datos de código.

Reinicia el laboratorio, repite el mismo marcador y verifica que ahora se muestre literalmente y que el atributo del body no aparezca.

5. Limpiar comentarios

curl -i -X DELETE http://127.0.0.1:8080/api/comments
